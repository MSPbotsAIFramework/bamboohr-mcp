## Requirement understanding

One line: wrap BambooHR's "List Time Off Requests" endpoint as a callable assistant/chat tool (`bamboohr_list_time_off_requests`), so the Daily/Weekly Attendance SOP can populate the Leave Status section with real BambooHR leave data instead of compiling it manually or from indirect sources.

Restated:
- Whose problem this solves: the people running the Daily/Weekly Attendance SOP (leadership / HR attendance reporting).
- What problem this solves: today the assistant has no tool that can read BambooHR's time-off request data, so the Leave Status section can only be filled manually or pieced together from indirect sources.
- What success looks like: the assistant can call a new tool with a date range (single day or full week) and get back structured leave records (employee name, employee ID, leave type, start/end date, status, duration) for generating the Leave Status section.
- The ticket's original "Existing Capability Check" says "verified in the wiki that the BambooHR connector exists and provides runtime tools, covering employee and time-off data, but did not confirm a ready-made tool equivalent to `bamboohr_list_time_off_requests`" -- this matches this round's code-level verification (see "Current state" below), so it is treated as a new capability request, not reinventing something that already exists.

## Product design

### Goals / Non-goals

**Goal**: add one callable, read-only assistant/chat tool `bamboohr_list_time_off_requests`, with required `start`/`end` date inputs, optional filtering by `status`/`employeeId`/leave type, returning structured JSON (at minimum employee name, employee ID, leave type, start/end date, status, duration/amount) for the Daily/Weekly Attendance SOP to generate the Leave Status section.

**Non-goals**:
- Not building "the assistant auto-generates the full Leave Status write-up" -- that is an SOP/prompt-layer concern, out of scope for this MCP tool.
- Not adding a helper tool to "look up leave-type ID by name" (e.g. `bamboohr_list_time_off_types`) -- the ticket only asks for this one tool; the type-ID availability question is recorded in Open Questions and does not block this ticket.
- Not changing `mcp-service-gateway` / `mspbots-agent-mcp` -- both are pass-through gateways, verified by code not to need changes (see "Current state").
- Not normalizing units for the `amount`/`duration` field -- passed through as-is from the upstream response.

### Acceptance criteria AC1..ACn

- **AC1**: Given valid BambooHR domain/api-key credentials are configured, When the assistant calls `bamboohr_list_time_off_requests` with `start`/`end` for a single calendar day, Then it returns a structured JSON array where each record includes at least employee name, employee ID, leave type, start date, end date, status, duration/amount (if provided upstream).
- **AC2**: Given the same credentials, When passing a `start`/`end` date range covering a full week, Then all matching records within that week are returned, not just a single day.
- **AC3**: Given a `status=approved` filter is passed, When calling this tool, Then the returned results only include records with status approved.
- **AC4**: Given an `employeeId` filter is passed, When calling this tool, Then only that employee's records are returned.
- **AC5**: Given no BambooHR credentials are configured (gateway mode missing the `domain`/`api-key` header, or env mode missing the environment variables), When calling this tool, Then a clear "missing credentials" error message is returned, with no unhandled exception raised.
- **AC6**: Given the BambooHR upstream returns an error status code (e.g. 400/401/403), When calling this tool, Then the tool forwards the upstream error status code and description verbatim to the caller, without silently swallowing it.
- **AC7**: Given there are no leave records in the queried range, When calling this tool, Then an empty array is returned rather than an error.
- **AC8**: Given two different tenants (different domain/api-key) call this tool concurrently, When the requests happen at the same time, Then each only gets back its own tenant's data, with no cross-contamination (multi-tenant isolation).

### Open Questions

- **[Assumed]** The ticket's original Open Question, "should the default return only approved requests, or require explicit `status=approved`" -- this design assumes: the tool sets no default and forwards BambooHR's `status` filter semantics verbatim (not passing it means no filtering, returning all statuses), leaving it to the SOP-side prompt to explicitly pass `status=approved` when needed. If this does not hold, "Option 4.3" and the tech design's "Change list" need to be redone.
- **[Non-blocking]** "Should the response fields standardize the `amount`/`duration` format" -- the MVP passes through the upstream JSON as-is with no normalization; a mapping layer can be added later if SOP generation quality is shown to suffer because of it (see tech design §10 Follow-up iterations).
- **[Non-blocking]** "The `type` filter needs a BambooHR numeric type ID rather than a readable name" -- this ticket does not provide a name-to-ID lookup tool; if the SOP wants to use this filter it needs to already know the tenant's time-off type id; recorded under Non-goals.
- **[Assumed]** "Which BambooHR account" -- reuses the existing gateway credential model (domain+api-key passed per request), identical to the other four tools, with no extra tenant/credential-resolution logic needed. If this does not hold (e.g. cross-account aggregation is needed), the tech design's "Non-functional - multi-tenant isolation" section needs to be redone.
- **[Assumed]** The response fields assumed in the tech design (`employeeId`/`name`/`type.name`/`start`/`end`/`status.status`/`amount`) come from BambooHR's public API docs; this round of design had no real tenant credentials available to verify them on the ground. A manual test case, TC-BTO-020, has been scheduled to verify this once with a real/sandbox account during self-test; if the field names don't match, the tech design's "Data and interface contract" needs to be redone.

## Technical design

### Conclusion

Add one read-only tool, `bamboohr_list_time_off_requests`, to the `bamboohr-mcp` repo, passing through to BambooHR's existing `GET /v1/time_off/requests` endpoint. Reuse the repo's existing `BambooHRClient`/credential isolation/error-handling mechanisms; no new dependency, no change to the upstream gateway. This is the cheapest approach for this repo: the existing four tools have already proven out the "read a BambooHR read-only endpoint" path three times (get/list/list_fields); the new tool is simply the fifth reuse of the same shape.

### Where the existing implementation lives

- `src/bamboohr_mcp/tools/employees.py:132-146` `bamboohr_list_employees` -- a ready-made template for the same kind of "parameter-less read-only list" tool: `register()` decorates with `@mcp.tool()`, pulls a client via `client_factory()`, requests via `client.get(path)`, serializes via `_dump()`, catches and forwards `BambooHRError`.
- `src/bamboohr_mcp/tools/employees.py:107-130` `bamboohr_get_employee` -- a template for a "read-only tool with query parameters," showing how optional parameters are passed through into `params=` and allowed to be `None`.
- `src/bamboohr_mcp/api_client.py:45-54` `BambooHRClient.get()` -- the generic GET wrapper; `_clean_params` already strips `None` values from the query (`api_client.py:40-43`), which the new tool's optional filter parameters benefit from directly.
- `src/bamboohr_mcp/server.py:144-147` -- the single entry point for tool registration; the new module only needs one added line, `time_off.register(mcp, client_factory)`.
- `tests/test_tools.py:1-104` -- the existing respx-mock test template; the three helpers `_client()`/`_basic()`/`_text()` can be reused directly.

### Option selection

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A: add a standalone `tools/time_off.py` module | Build a separate module shaped like `employees.py`, add one registration line in `server.py` | Consistent with the repo's existing convention of "splitting modules by resource" (`tools/` currently has only `employees.py`, but its naming and responsibility boundary already imply "split by resource"); smallest change surface, pure addition | No real cost | **Adopted** |
| B: fold the new tool into `employees.py` | One fewer file | Saves one import | `employees.py`'s docstring (`employees.py:1-9`) explicitly states "employee creation primarily, with supporting read operations"; mixing in a leave-time resource would blur the module's responsibility and make the module name inaccurate | Not adopted |

No need to consider "modify an existing tool" type options -- this is a pure addition of new capability that does not affect any existing behavior of the four existing tools.

### Data and interface contract

**MCP tool signature** (for assistant/SOP calls):

```
bamboohr_list_time_off_requests(
    start: str,                       # required, YYYY-MM-DD
    end: str,                         # required, YYYY-MM-DD
    status: str | None = None,        # optional: approved / requested / denied / canceled / superseded
    employee_id: str | None = None,   # optional, mapped to upstream employeeId
    time_off_type_id: str | None = None,  # optional, mapped to upstream type (numeric type ID, not a name)
) -> str  # JSON array text, serialized via _dump()
```

**Upstream API** (BambooHR gateway, pass-through):

```
GET {BAMBOOHR_API_ROOT}/{domain}/v1/time_off/requests
Query: start, end, employeeId, status, type
Auth: HTTP Basic (username=api-key, password=BAMBOOHR_BASIC_PASSWORD, same as the existing 4 tools)
```

Example response (**field names come from BambooHR's public API docs, not verified against a real tenant for this org** -- see Open Questions and TC-BTO-020):

```json
[
  {
    "id": "1204",
    "employeeId": "37",
    "name": "Ada Lovelace",
    "status": { "status": "approved", "lastChanged": "2026-08-20", "lastChangedByUserId": "9" },
    "start": "2026-09-08",
    "end": "2026-09-08",
    "created": "2026-08-20",
    "type": { "id": "1", "name": "Vacation" },
    "amount": { "unit": "days", "amount": "1" },
    "dates": { "2026-09-08": "8" }
  }
]
```

- **Error codes**: all 4xx/5xx go through the existing `BambooHRError` (`api_client.py:73-83`) -- the tool returns `"Error: BambooHR API error <code>: <detail>"`, with `<detail>` preferring the upstream `X-BambooHR-Error-Message` header when present.
- **DB changes**: none, this tool does not persist anything or add any table.
- **Events/messaging**: none.
- **Backward compatibility**: a pure addition; does not affect existing callers of `bamboohr_create_employee`/`bamboohr_get_employee`/`bamboohr_list_employees`/`bamboohr_list_fields`; the tool list returned by MCP `tools/list` will have one more entry, and callers invoke by tool name, so there is no scenario where an old client breaks because of this.

### Key flow sequence

```
SOP/assistant -> mcp-service-gateway(/mcp) -> bamboohr-mcp(/mcp, tools/call)
  1. The assistant decides it needs to generate Leave Status, calls bamboohr_list_time_off_requests(start, end[, status][, employee_id])
  2. mcp-service-gateway passes the request through per the bamboohr entry in vendor/registry.yaml (does not parse the tool name)
  3. bamboohr-mcp's GatewayCredsMiddleware validates the domain/api-key headers are present (missing -> 401, tool code does not run)
  4. The tool function inside time_off.register pulls client_factory() -> BambooHRClient.get("/time_off/requests", params)
  5. BambooHRClient makes an HTTP Basic Auth request to the BambooHR gateway
  6a. Success -> _dump(result) returns the JSON array text verbatim
  6b. Upstream 4xx/5xx -> BambooHRError -> the tool returns "Error: ..." text
```

### Non-functional

- **Idempotency and concurrency**: a read-only GET, naturally idempotent, repeated calls have no side effects; concurrent requests are isolated via `contextvars` (`server.py:18-23`), sharing the same mechanism as the existing four tools, with no new locking or de-duplication logic needed.
- **Performance**: per public docs, this BambooHR endpoint does not support pagination; a single request returns all matching records within the `start`~`end` range, with no client-side rate limiting on response size for very large companies + very long date ranges. The ticket's use case is "daily/weekly SOP scheduled trigger," not a user-interactive real-time path, so no dedicated performance optimization is judged necessary right now; neither the ticket nor the product design gives an explicit SLA, recorded as a known gap (TC-BTO-014, `[INCOMPLETE requirement]`); recommend the SOP side keep query granularity at the day/week level rather than month/year.
- **Security**: the auth point is identical to the existing four tools (Basic Auth + per-request header isolation); no new privilege-escalation surface is added (no writes, no new credential-storage path exposed); on logging, this repo currently has no structured logging infrastructure (`server.py`/`api_client.py` each have just one `print`-to-stderr warning); this tool adds no extra logging, keeping the repo's current state as-is -- adding logging infrastructure is out of scope for this ticket.
- **Multi-tenant isolation**: the tenant dimension lives entirely in the two request headers `domain`/`api-key`; `contextvars` guarantees concurrent requests do not cross-contaminate (AC8/TC-BTO-011); there is no cross-tenant shared cache or global state.
- **Observability**: no new metrics/logging, consistent with the repo's current state; when something goes wrong, the troubleshooting path is the same as the existing four tools -- `BambooHRError` carries the upstream status code and `X-BambooHR-Error-Message`.

### Rollout and rollback

- No feature-flag mechanism (this repo has no flag framework at all); the new tool takes effect as soon as the image ships -- an MCP tool is "callable once registered"; the assistant/SOP prompt side additionally needs to know this tool's name to use it, which amounts to a soft rollout gate.
- Release order: a single-repo change (`bamboohr-mcp`), with no dependency on a synchronized release of `mcp-service-gateway` or `mspbots-agent-mcp` (both verified by code to be pure pass-throughs, see "Current state").
- Rollback: revert this ticket's commits, rebuild the Docker image, and redeploy; no DB migration, no data change, zero residue on rollback.

### Test strategy

- **Unit tests**: `tests/test_time_off.py`, pytest + pytest-asyncio + respx (reusing `tests/test_tools.py`'s existing approach), covering all 19 `type: auto` cases in `docs/tickets/PRD-18270.ac.json` -- happy path (single day/full week/filters), missing credentials, upstream 4xx forwarding, empty results, missing required parameters, invalid enum value pass-through, concurrent multi-tenant isolation.
- **Manual verification**: TC-BTO-020 (check response fields against the tech design's assumptions using a real/sandbox BambooHR account) -- since the field names in the contract come from public docs and have not been verified against a real tenant for this org, this step cannot be skipped.
- **Regression surface**: pure new file + one registration line in `server.py` + README docs, not modifying a single line of `employees.py`/`api_client.py`/`config.py`; so `bamboohr_create_employee`/`bamboohr_get_employee`/`bamboohr_list_employees`/`bamboohr_list_fields` and the existing cases in `tests/test_tools.py`/`tests/test_middleware.py` are unaffected, with a theoretical regression surface of zero; still recommend running the full existing test suite once to confirm.

### Effort and breakdown

Rough estimate: **0.5-1 person-day** (a single new tool module + matching unit tests + README docs, copying the pattern already established in the repo; the main uncertainty is whether TC-BTO-020's real-field verification will expose a contract mismatch). Small in scope, not recommended to split into sub-tasks; a single PR covering implementation + tests + docs can be accepted in one pass.

### Risks and dependencies

- **Risk**: the response-field assumption has not been verified against a real tenant (see Open Questions) -- mitigated by TC-BTO-020's manual verification, scheduled as the first step of self-test; if fields don't match, cost of coming back to fix the contract is manageable.
- **Risk**: this design did not verify, one by one, the legal value range for the `status`/`type` enums (relying on BambooHR's public docs); if the upstream's actually-supported values differ from the docs, AC3/AC6's judgment is unaffected (this tool already does no local enum validation, it only passes through), but the SOP prompt side's assumptions about legal values may need adjusting accordingly -- that layer is out of scope for this ticket.
- **Dependency**: no dependency on any other in-flight ticket; `bamboohr-mcp` repo access and the Code Project field option have both been confirmed ready in this ticket's comment history (`90170249205590`, `90170249474689`).
